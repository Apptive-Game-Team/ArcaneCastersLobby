# 친구 접속 상태와 친선전 초대 전달 확인

친구 목록의 `status`는 접속 heartbeat를 기준으로 `Offline`, `Online`,
`OnMatching`, `OnPlaying`을 반환한다. 접속 저장소나 상태 조회에 실패하면 `Unknown`으로
반환한다. DB의 `user_status`는 변경하지 않는다.

- `POST /api/friends/presence`: 인증된 본인의 Redis 접속 TTL을 35초로 갱신한다.
  클라이언트는 로그인 중 모든 화면에서 약 10초마다 호출한다. 종료나 통신 단절 후
  TTL이 지나면 오프라인이다. 목록은 5초마다 갱신하므로 화면 반영은 추가로 지연될 수 있다.
- `POST /api/friends/{friendId}/invite`: 양쪽 접속 상태가 `Online`이고 덱이 유효할 때 생성한다.
  성공 응답은 상대 수신을 보장하지 않는다.
- `POST /api/friends/invites/{inviteId}/received`: 수신자만 호출한다. 초대 창 표시 후
  호출하며 최초 `deliveredAt`을 보존한다. 재호출은 멱등적이다. 종료된 초대는 변경하지 않는다.
- `GET /api/friends/invites/sent`: 본인이 보낸 최근 5분 이내 초대를 반환한다.
  `deliveredAt == null`이면 전달 대기, 값이 있으면 상대 클라이언트의 수신 확인이다.
  사람이 내용을 읽었다는 뜻은 아니다.
- 기존 `/invites/pending`은 수신한 대기 초대를 생성 시각순으로 반환한다.

초대 DTO의 `revision`은 변경마다 증가한다. 클라이언트는 더 낮거나 같은 revision의
응답을 최신 상태 위에 덮어쓰지 않는다. `expiresAt`은 화면을 다시 열어도 연장되지 않는다.
SSE는 빠른 알림에 사용하고, 5초 주기 조회로 누락을 복구한다.

## 적용 범위와 배포

서버를 먼저 배포한 뒤 클라이언트를 배포한다. 구버전 클라이언트는 heartbeat와 수신 확인을
보내지 않으므로 접속/전달 확인을 제공하지 않는다. 새 클라이언트와 함께 배포해야 한다.

초대 저장소와 SSE는 기존 프로세스 메모리 구조를 유지한다. 다중 lobby 인스턴스 간 초대
공유나 재시작 후 복구는 제공하지 않는다. 방 생성 중 동시 수락 및 취소와의 경쟁, 방 생성
결과를 알 수 없는 네트워크 오류의 복구는 별도 작업이다. 이번 변경은 기존 accept 완료 시
최신 수신 시각과 revision을 보존하지만 방 생성 자체의 중복 실행을 해결하지 않는다.
